# 0.1.2 review findings and decisions

Reviewed 2026-09-05 against `fdc9b7b` and the published 0.1.1 artifacts.
The supplied review targeted 0.1.0 and proposed reusing 0.1.1. Version 0.1.1
is now published; its four PyPI and GitHub Release digests match the retained
manifest and its live description contains the corrected installation text.
Neither published version nor tag will be replaced. The next proposed release
is 0.1.2, subject to the decisions below.

## Implementation decision

The maintainer authorized implementation and publication after reviewing these
findings. The accepted scope preserves the verified MLX bound and strict CPU
fallback. At the maintainer's request, the README omits the 20-chunk attempt;
the hardware record describes it as inconclusive under reduced torque while
retaining the unmet return check, nonzero exit, torque-off cleanup, and
unresolved causal attribution. The earlier review recommendations below are
historical, not an outstanding approval gate.

Installed lab modules now use the private namespace through explicit
setuptools package-directory mapping. Repository source paths stay unchanged
to preserve provenance. Pre-1.0 dependency ranges retain tested minor lines.
The PyPI Trusted Publisher settings page requires password confirmation;
local Keychain publication remains available and authorized.

## Native extension and compatibility

`otool -L` shows `@rpath/libmlx.dylib`. Native sources include MLX allocator,
CPU encoder, ops, primitives, arrays and stream headers. The extension is
therefore bound to the MLX C++ ABI. `rmsnorm.py` restricts active native calls
to MLX 0.32.2 and catches ImportError during import.

Fresh 0.1.1 installed-wheel probes:

| MLX | Native import | Active CPU backend | Result |
| --- | --- | --- | --- |
| 0.32.0 | Unavailable, caught by import fallback | pure-mlx-fallback | Import and doctor succeed; doctor reports verified. |
| 0.32.2 | Available | native-reference | Import succeeds; installed release doctor check succeeds. |
| Newest 0.32.x | PyPI currently lists 0.32.2 | Same case as above | No additional version available to test. |

The retained compatibility evidence already verifies strict deterministic gates
on 0.32.0 and 0.32.1 using the pure-MLX fallback. The proposed strict-mode error
would contradict those results. Keep `mlx>=0.32.0,<0.32.3` until additional
versions are tested; widening to `<0.33` admits future unverified patch versions.
Additional OSError/RuntimeError handling and better backend diagnostics may be
reasonable, but require a targeted behavior test and accurate fallback wording.

A pure-Python core/strict-extra split needs packaging, diagnostics, and support
contract decisions. It cannot be justified as an unreviewed sub-50-line tweak.
Track it separately rather than changing this release's numerical behavior.

## 20-chunk hardware decision — review stop point

The retained profile is torque limit 100 (10% of the documented scale). The
return-position check exhausted its 20-step cap as gravity-loaded joints stopped
following return commands. The process exited 1; telemetry records session_start
and session_error with `hardware cleanup failed (1 sub-exception)`. The I/O trace
has 388 entries. The observer also records primary_exit_code 1. Retained
preflight evidence confirms all-six torque-off cleanup and subsequent inset,
zero-drift/profile/calibration checks.

The telemetry does not retain a complete per-chunk validity/protocol summary.
Thus it does not establish the review's required assertion that every chunk
was valid and no serving/policy fault occurred. Reduced torque is consistent
with the observed return problem, but the available records do not isolate it
as the sole cause. A pending nominal-torque rerun cannot supersede an actual
failed result. No hardware access or motion was performed during this review.

The supplied Phase 0.3 says to stop and leave hardware text unchanged when logs
are insufficient. FIRST_CONTACT, README hardware text, numerical thresholds,
and existing result evidence have therefore remained byte-identical in this
review. Maintainer decision: preserve the failure and move its README placement,
or request further diagnosis before editing its characterization.

## Release infrastructure corrections

- Current CI is intentionally disabled pending a suitable seeded self-hosted
  runner. Do not blindly enable model/evidence-dependent tests on an empty
  hosted runner. Packaging checks can be split into a hosted job first.
- Current GitHub documentation lists standard macos-14 as arm64, so that part
  of the review is correct. Its image is being deprecated; choose and verify
  an available arm64 image plus an explicit macOS deployment target.
- Require architecture/Metal availability checks for any selected inference
  smoke. Do not promise the full local evidence suite on hosted CI.
- Trusted Publishing needs PyPI publisher registration. GitHub environment
  required-reviewer configuration is a preference, not a technical requirement;
  adding an obligatory click conflicts with the request for autonomous uploads.
- The API token is confirmed present in macOS Keychain. Future authorized local
  uploads can use `uv publish --username __token__ --keyring-provider subprocess`
  with the explicit macOS keyring backend; never print the credential.
- No token was revoked and no new public version/tag was created for this review.
  Completing the already-authorized 0.1.1 GitHub Release is recorded above.

Sources: https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job
and https://github.com/actions/runner-images/blob/main/images/macos/macos-14-arm64-Readme.md

## Proposed implementation order after judgment

1. Move lab code into a private package namespace; isolate the build backend;
   add installed-wheel layout and decoy-cwd tests; preserve evidence identifiers.
2. Evaluate dependency ranges against the unchanged lock and concrete clean /
   prepopulated environments. Keep the verified MLX bound and CPU fallback.
3. Rewrite the README with absolute release links, simpler voice, and hardware
   evidence below usage; preserve the failed-return limitation. Adjust the
   upstream example budget if the maintainer accepts that numerical edit.
4. Add hosted packaging CI and prepare Trusted Publishing separately from the
   seeded local numerical lane. Draft the upstream issue without sending it.
5. Run the complete final suite and artifact install matrix, then build from
   the verified 0.1.2 source checkpoint. Never republish or retag 0.1.1.
